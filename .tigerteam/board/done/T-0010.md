### Notes for the reviewer
- **Per-frame allocations.** `main.ts`'s frame loop itself does not
  allocate: `hudValues`, `state`, `resolveMove`, and the reused API
  object are all created once outside the loop, and scalar fields of
  `state` are copied from `stepPlayer`'s return in place. Two
  unavoidable allocations remain inside downstream code, out of scope
  for this ticket:
  1. `Controls.readInput()` builds a fresh `InputState` object each
     call (`src/player/controls.ts:117`). Could be turned into a
     mutable field with a `readInputInto(target)` variant in a follow-up.
  2. `stepPlayer` internally allocates its `from`/`to` `Vec2` tuples
     and the returned `PlayerState` — the ticket calls the returned
     object out as the "one allowed allocation"; the `from`/`to`
     tuples fall under the same call.
- **Facing on spawn.** `syntheticCity()` starts with a building
  centred at world origin, so `(0, 0)` is inside a footprint —
  `findSpawnX` walks +x until the first free cell. With the default
  seed the first free spot happens to be `x = 0` because the ring
  passes exactly through the origin (blocked returns false at the
  edge). Not a bug — matches the spec verbatim ("if `(0,0)` is
  `blocked`, walk +x").
- **404 in devtools.** Chromium logs one 404 on load — it's the
  favicon fetch (`/favicon.ico` isn't shipped). Non-blocking; a
  favicon can land in a follow-up ticket.
- **Overlay CSS.** Kept the `#overlay.resume` variant minimal (just a
  smaller prompt + slightly lighter dim). Full "smaller overlay"
  polish (opacity/anim) is out of scope.
- **T-0013.** The controls-held-key bug flagged in earlier PM notes
  still applies but is intentionally not addressed here (out of
  `src/player/` scope for this ticket).
