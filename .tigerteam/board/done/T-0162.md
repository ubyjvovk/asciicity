## Goal
Wave 22 will rebuild central Tokyo from Project PLATEAU (MLIT's open 3D city
models) instead of / on top of OSM. Before the PM can write production
tickets, find out — with measured facts, not assumptions — how to get the
data, what it contains over OUR Tokyo extent, and how it maps onto our
schema. Deliver a design doc with evidence and a working prototype on one
1 km cell. This is research + prototype: judgment is expected (C3); flag
anything that contradicts the assumptions below.

## Context
- Our Tokyo: `public/data/tokyo/` (tiled, 28 MB), bbox lon 139.692–139.820,
  lat 35.645–35.715, origin 139.7671, 35.6812 (Tokyo Station). Built by
  `npm run fetch-data:tokyo` (OSM + DEM). Schema: `src/data/types.ts`
  (`Building` with `h`, `minH`, `poly`, and since wave 21 optional `roof`
  {shape, h, dir}, `osmColor`, `roofColor`, `material`); format rules
  docs/data-format.md (read "Tiled datasets", "Building parts", "Simple 3D
  Buildings"). Coordinates: x east, z SOUTH, metres from origin
  (`project()` in `scripts/osm-convert.mjs`).
- PM's current understanding (verify each): PLATEAU publishes CityGML
  (LOD1 footprint+`measuredHeight` for all 23 wards; LOD2 roofs for central
  districts, some textured), plus derived 3D Tiles / MVT / other formats via
  the G空間情報センター (geospatial.jp) catalogue and PLATEAU VIEW; licence =
  PLATEAU site policy, stated compatible with CC BY 4.0 (our project is
  CC BY-NC-SA 4.0 — BY content can be included with attribution).

## Questions the doc must answer (with numbers / URLs / quotes)
1. **Access**: exact dataset(s) and URLs for Tokyo 23 wards (latest year);
   download size of the parts covering our bbox; which format is most
   practical for a Node 22 script with no new npm deps (CityGML/XML parse
   by hand? GeoJSON/GeoPackage/MVT variants? 3D Tiles?). The worker image
   is offline-capable only for npm ci — network is available for downloads;
   cache raw downloads under `.cache/plateau/` (gitignored — add nothing to
   .gitignore; if `.cache/` is not ignored, block and ask).
2. **Licence**: quote the terms and attribution text; confirm (or refute)
   compatibility with CC BY-NC-SA 4.0 redistribution of DERIVED JSON in
   `public/data/`.
3. **Coverage over our bbox**: building count LOD1 vs LOD2 (vs our OSM
   count in `public/data/tokyo/`); share of LOD2; which attributes exist
   (measuredHeight, storeys, usage, roof type?, textures?).
4. **Mapping**: how LOD1/LOD2 map onto `Building` — footprint source,
   height (measuredHeight vs OSM), `roof` inference from LOD2 roof surfaces
   (gabled/hipped/... or "complex"), colours from textures (mean colour?),
   material. What CANNOT be represented (e.g. arbitrary LOD2 roofs,
   stepped towers) and a recommendation: extend the schema (PM decision —
   propose the exact type) vs approximate.
5. **Merge with OSM**: keep OSM roads/water/names/parts and replace or
   augment building geometry? Matching strategy (footprint overlap IoU?),
   measured match rate on the prototype cell.
6. **Size / performance**: projected tile JSON size for the whole bbox vs
   today's 28 MB, with the recommendation.

## Prototype
- `scripts/plateau/` — a Node 22 ESM script (no new deps) that converts the
  PLATEAU data for ONE 1 km cell around Tokyo Station (our tile `0_0`) into
  our `Building[]` (projected with the same `project()` / origin), writes it
  to `.cache/plateau/out/0_0.json` (NOT public/data), and prints coverage /
  match stats. Pure helpers exported + `tests/plateau.test.ts` covering them

Key findings (details + evidence in the doc):
- **Access**: latest = FY2025, spec 5.0, **per-ward** datasets
  (`plateau-131xx-<ward>-2025` on geospatial.jp), not the FY2020 `13100`
  23-ward bundle. The PLATEAU data-catalog API
  (`https://api.plateau.reearth.io/datacatalog/citygml/m:<mesh>`) returns
  per-mesh file URLs + feature/LOD counts; the files are served gzip-encoded
  (8:1), so Node 22 `fetch` gets single mesh GMLs directly — no zip, no deps.
  Our bbox = 99 meshes, 6.75 GB GML ≈ 0.85 GB on the wire (whole ward zips:
  12.7 GB). CityGML chosen over 3D Tiles (no roof/wall semantics) / MVT
  (FY2025 buildings not published as MVT) / FBX-OBJ (discontinued).
- **Licence**: PDL 1.0, explicitly CC BY 4.0-compatible (quoted) → derived
  JSON under CC BY-NC-SA OK with attribution + "modified" notice; proposed
  attribution text in the doc. One caveat flagged (Survey Act note).
- **Coverage**: ≈ 195 k PLATEAU buildings in the bbox (area-weighted catalog
  counts) vs 170.6 k OSM; ≈ 35–37 % LOD2; `measuredHeight` on 97–98 %.
  86 % (tile 0_0) / 98 % (tile -4_-3) of shipped OSM buildings sit at a
  converter DEFAULT height — heights are the big win.
- **Mapping**: LOD1 maps 1:1; LOD2 roofs classify to our roof shapes for only
  ~6 % of LOD2 buildings; 48 % are stepped/complex. Option A (no schema
  change, extra grounded prisms per roof-height tier) measured: +120 % bytes
  on 0_0 with per-tier colour/detail side effects. **Recommended Option B:
  optional `Building.tiers?: { h; poly }[]`** (exact type in the doc) — PM
  decision, NOT implemented (types.ts untouched).
- **Merge**: IoU ≥ 0.5 matches 78.9 % (0_0) / 77.8 % (-4_-3) of PLATEAU
  buildings; OSM names transferred for 338/366 named; 83 / 130 OSM buildings
  per tile not covered by PLATEAU → keep them. Rules 1–4 in the doc.
- **Size**: ≈ 35 MB whole dataset with LOD1 envelopes, ≈ 45 MB with LOD2
  tiers (today 28.3 MB; budget 60 MB).
