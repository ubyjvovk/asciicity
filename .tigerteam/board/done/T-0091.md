## Goal
User report: after the pointer lock is lost by an OS action (macOS
screenshot shortcut), the game cannot regain it short of a reload — keys
work, Escape does nothing, no overlay. Root cause in the code: a rejected
`requestPointerLock()` is swallowed at every call site, there is no
`pointerlockerror` listener, and Escape has no handler outside the
browser's own lock-exit event. Make lock failures visible, Escape always
functional, and the game playable without a lock. Contract:
`docs/architecture.md` §4.7 "Wave 10 amendment (T-0091)" — read it first;
it is the spec.

## Context
- `src/player/controls.ts`: drag-to-look when unlocked (`mousedown` →
  `mousemove` clientX/Y deltas → `lookDx/lookDy`, same sensitivity as the
  locked path, `isMouseSpike` filter; end on `mouseup`/`mouseleave`);

  browsers returning `undefined` still work) and calls a constructor-
  provided `onLockError(reason: string)` on rejection; also listen for

  main.ts's own two `requestPointerLock()` calls through the same error
  path. Keep everything else in main.ts untouched.
- `src/hud/hud.ts`: the help line shows `DRAG LOOK` instead of `MOUSE
  LOOK` while `pointer.dragLook` is true (find how the help line is

## Rework (attempt 2)

### PM rework note 1 (2026-08-29)

Host gate: `e2e/pointer.spec.ts` fails deterministically on the host (twice)
while it passes in your container. Replaying the steps with 300 ms between
the two overlay clicks passes on the host too (`click2 → dragLook: true,
failures: 2`), so the difference is speed: Playwright's second click lands
inside `reportLockError`'s **50 ms `lockErrorBurst` window**, and the second
attempt's rejection is dropped as a duplicate of the first. Result: the
overlay is hidden, `failures` stays 1, `dragLook` stays false — the player
is stranded exactly the way this ticket is meant to prevent (a real user
double-clicking fast hits it).

**Fix — coalesce per attempt, not per wall-clock window:**
- `requestCanvasLock()` creates an attempt object `{ settled: false }` and
  stores it as `currentAttempt`. The promise's rejection / "fulfilled but
  unlocked" path and the `pointerlockerror` listener all call
  `settleAttempt(reason)`, which does nothing if `currentAttempt.settled`
  is already true, otherwise marks it settled and runs the failure logic
  (`failures += 1`, prompt / drag-look). A `pointerlockchange` that grants
  the lock also settles the attempt (as success). Delete `lockErrorBurst`
  and the `setTimeout`.
- Same per-attempt rule for `Controls.onClick` (it reports through
  `onLockError`; main.ts's `settleAttempt` must treat a report that arrives
  with no pending attempt as a NEW single failure, never drop it).
- Add a unit case to `tests/controls.test.ts` or a small main-level pure
  helper test: `'two rapid failed lock attempts count as two failures'`
  (two requests back-to-back, both rejecting → `failures === 2`).

Keep `e2e/pointer.spec.ts` as it is — it must pass on the host without
extra waits. Rerun `bash .tigerteam/scripts/run-tests.sh
tests/controls.test.ts` and `bash scripts/check.sh`, then hand off with

- `hud.ts` / `e2e/pointer.spec.ts` unchanged from attempt 1 (still on the branch from `aa1995b`).

### How the host failure is fixed
Playwright's second overlay click used to land inside the 50 ms `lockErrorBurst` window, so that attempt's rejection was dropped — overlay hidden, `failures` 1, `dragLook` false. Now every `requestCanvasLock()` allocates a fresh attempt token, so the second click is an independent attempt: click 1 → `failures = 1` + DRAG TO LOOK prompt; click 2 → `failures = 2` + `dragLook = true`. This is timing-independent.
