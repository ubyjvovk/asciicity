## Goal
Entering Tokyo switches the render style to `matrix` automatically (user
ask). Mechanism: an optional per-city default style in the registry, with
a locked precedence order — an explicit `?render=` always wins, and the
user's persisted choice still applies everywhere else.

## Context
- **Read first**: architecture.md §4.20 "Per-city default render" — the
  precedence chain is locked:
  `renderFromUrl(location.search)` → `city.defaultRender` →
  `settings.render` → `'ascii'`.
- `CityInfo` (src/data/cities.ts) gains `defaultRender?: string`
  (a `STYLE_ORDER` id); the tokyo entry sets `defaultRender: 'matrix'`.
  No other city sets it.
- `src/main.ts`: the initial style currently comes from the merged
  settings (`opts.render`). Change the pick to the §4.20 chain — note it
  can only be evaluated AFTER the city is resolved (picker included).
  `settings.ts` already exports the URL parser; do not change
  `settings.ts` semantics, persistence, or the share-URL rewrite. `R`
  cycling and its persistence stay exactly as they are; `?synthetic=1`
  ignores city defaults (no city).
- An unknown `defaultRender` id must fall through to the next link in the
  chain (cities.ts should never carry one, but be safe).
- e2e: extend `e2e/tokyo.spec.ts` — plain `?city=tokyo` boot reports
  `window.__asciicity.render === 'matrix'`; `?city=tokyo&render=ascii`
  reports `'ascii'` (explicit URL wins).
- If `tests/settings.test.ts` does not exist, put the precedence unit
  tests in `tests/cities.test.ts` and say so.

### Why the precedence tests live in tests/cities.test.ts (ticket's "say so" clause)
The chain function is exported from `src/data/cities.ts` because that is the only
in-scope pure module that can host it: `src/settings.ts` is read-only per the
out-of-scope fence, and `src/main.ts` cannot be imported by node tests (it imports
`./style.css` and runs `void main()`). Per the ticket's conditional, I therefore
put the precedence unit tests in `tests/cities.test.ts` rather than
`tests/settings.test.ts`.
