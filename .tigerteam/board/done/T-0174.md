## Goal
T-0171 added the bottom-left `#busy` status line (read `docs/hud-busy.md`
and `src/hud/busy.ts` first). It is hidden until `loading.phase === 'ready'`.
The user: "initial loads now take several seconds, so let's show the loading
indicator right from the start (would be cool if it was something
lore-appropriate)". Show it from the first paint of the page through the
whole boot, with cyberpunk-terminal wording, then hand over to the existing
background-sync behaviour unchanged.

## Design (LOCKED — flag, don't redesign)
**From the first byte.** Add static markup to `index.html` (inside `<body>`,
before the module script): `<div id="busy" class="on boot">` containing
the same three spans BusyView uses (`.busy-head`, `.busy-bar`,
`.busy-label`) with initial text `⠋ JACK-IN ▱▱▱▱▱▱▱▱ LINKING NODE`. A tiny
pure-CSS animation (in `src/style.css`, or an inline `<style>` in
index.html if style.css is not loaded before the bundle — check, and pick
whichever shows it on the first paint) pulses the bar so the page is alive
before any JS runs. `BusyView` must ADOPT an existing `#busy` element if
present (else create it, as today) — no duplicate ids.

**Boot phases → lore line** (pure, in `busy.ts`):
`bootLine(p: LoadProgress, cityLabel: string, tMs: number, narrow: boolean): string`
(`LoadProgress` from `src/ui/loading.ts`, read-only):
- before any progress / city picker shown: nothing new — keep the static
  `JACK-IN … LINKING NODE` line until the first progress event, and HIDE the
  line while the city picker waits for a click (nothing is loading);
- `download`: `⠹ JACK-IN ▰▰▰▱▱▱▱▱ DOWNLINK 4.2/14.7 MB` — here the 8-cell
  bar is DETERMINATE (filled = floor(received·8/total)), no ping-pong;
- `parse`: `⠹ DECRYPT ▱▰▰▰▱▱▱▱ CITYGRID <CITY>` (ping-pong bar);
- `build`: `⠹ COMPILE ▱▰▰▰▱▱▱▱ <STEP>` (the builder step, e.g. `TERRAIN`,
  `TILE 3_4`), `COMPILE ▱▰▰▰▱▱▱▱ <CITY>` when no step;
- `ready`: fall through to the existing `busyLine` (SYNC / BOOT, sectors,
  neon grid, cells, cars) — unchanged behaviour and wording.
Spinner/bar timing as in busy.ts (`SPINNER_MS`, `BAR_MS`); `narrow` drops
the label like `busyLine`.

**Visibility during boot:** shown regardless of the HUD setting (the HUD
is not up yet); `z-index` above `#overlay` (overlay is 10 → use 11 while
`.boot`); no 300 ms show-delay during boot (it is already visible from the
first paint); after `ready` the class `.boot` is removed and the existing
rules apply (HUD setting, hysteresis, 600 ms hold + fade). The `#overlay p`
loading text stays as is (e2e depends on it) — do not change
`formatLoading`.

**Colour:** boot uses the HUD green, with the same glow class
(`.neon`) applied when the requested style is `cyberpunk`
(`?render=cyberpunk` / saved setting) so a cyberpunk boot is already neon.

### For the reviewer
- **Signature deviation:** `bootLine` has an optional fifth parameter, `inputs: BusyInputs = idle`. The locked four-argument signature has no background inputs to delegate to at `ready`, so "bootLine ready === busyLine for the same inputs" needs them. Called with four arguments at `ready`, it returns `''` (idle `busyLine`).
- **Handover:** if the line is up at ready, `BusyGate.force` counts it as already shown. So an idle city holds the last boot text (for example `COMPILE … TILE -2_0`) for 600 ms, then fades. A busy one continues straight into SYNC/SECTORS without the 300 ms gap. After `.boot` is removed, `z-index` drops back to 6, below the `#overlay` (10) that is still showing CLICK TO ENTER. This follows "existing rules apply".
- **CSS ordering:** `#busy.boot.neon` is repeated inline, so the neon colour does not depend on whether `style.css` loads before or after the inline `<style>`.
- **Not covered:** if the boot throws before `ready` (not the synthetic fallback, which continues), the boot loop keeps spinning. This is an edge case I did not handle.
