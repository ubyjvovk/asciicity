## Goal
San Francisco is next, and its water is `natural=coastline` — ways, not
polygons — which the converter currently ignores entirely: the Bay would
render as flat walkable ground. Implement `docs/data-format.md`
"Coastline water" rules 1–6 exactly (read that section first; it is the
contract, including the clockwise boundary-closure walk, the island rule
and the flattening parity).

  `clipPolylineToBbox(points, bbox)`, `stitchChains(pieces)`,

### For the reviewer
- The CW perimeter walk is parameterised on `t ∈ [0, 4)` starting at the
  NE corner (east, south, west, north edges). Corners belong to the
  outgoing edge (NE → east at t=0, SE → south at t=1, etc.) — this
  matters at corner-hitting endpoints and is worth eyeballing in
  `closeCoastline` (`perim` helper).
- `clipPolylineToBbox` uses Liang–Barsky rather than reusing the
  Sutherland–Hodgman helpers (which are polygon-specific). The
  segment-by-segment approach mirrors the ticket's language and keeps
  the original vertices verbatim where they lie inside the bbox.
- Coastline rings are added to `water` **after** the standard
  `natural=water` polygons, which keeps the London/Kyiv output
  byte-identical (they emit no coastline rings) and orders coastline
  outer rings before their potential islands.

## Rework (attempt 2)

Strong work — Liang–Barsky clip, stitching, parity flattening and the
fixtures are all correct. One confirmed geometry bug in `closeCoastline`
blocks accept:

**Corner insertion ignores CW order.** The loop iterates the fixed
`corners` array `[SE, SW, NW, NE]` and pushes each qualifying corner
immediately. After shifting each corner's `ct` past `endT`, the array
order no longer matches walk order whenever `endT ≥ 1` (chain ending on
the south/west/north edge). Reproduced on your branch:

    closeCoastline([[[0.5, 0], [0, 0.5]]], {minX:0, minY:0, maxX:1, maxY:1})
    → [[0.5,0], [0,0.5], [1,0], [0,1], [1,1]]   // SE, NW, NE — bowtie

Correct walk from endT 2.5 to startT 5.5 passes NW(3), NE(4), SE(5):
`[[0.5,0], [0,0.5], [0,1], [1,1], [1,0]]`. Your existing fixtures all end
on the east edge (endT < 1), which is the one case where array order and
walk order coincide — SF's coastline will not be so polite.

Fix: collect the qualifying corners as `{ct, pt}`, sort ascending by the
shifted `ct`, then push. Add the fixture above to
`tests/coastline.test.ts` asserting the exact five-vertex ring, plus one
multi-corner variant that wraps t=4 (e.g. chain ending on the south edge
closing to a start on the east edge — corners SW, NW, NE in that order)
so the wraparound stays covered.

Everything else stands; keep the commits. Note: the smoke e2e failure you
diagnosed is fixed on main (T-0074 merged), so `check.sh` should now be
fully green — run it and report all four phases.
