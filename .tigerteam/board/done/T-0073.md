## Goal
The second half of `docs/architecture.md` §4.15 (read it first): a 3-second
· 12 fps · ≤ 960-px-wide animated GIF of the walk, downloadable with
`Shift+P` or the pause-menu `RECORD GIF (3S)` button. T-0072 landed the
module, the PNG path, the keys plumbing and the e2e file — extend them.

## Context
- `gifenc@1.0.3` is already in `dependencies` (`import { GIFEncoder,
  quantize, applyPalette } from 'gifenc'`). It has no bundled types: add a
  minimal ambient declaration (e.g. `src/export/gifenc.d.ts` — keep it
  inside `src/export/`, it is within scope as part of the module).
- `recordGif(download = true)` per §4.15: 36 frames captured from
  `afterRender()` every `floor(fps/12)`-ish — simplest correct rule: sample
  on a 83.3 ms wall-clock schedule (`performance.now()`), not frame count,
  so 30 fps and 144 fps machines both yield 3 s. Scale
  `min(1, 960 / canvas.width)`, `imageSmoothingEnabled = false`, caption
  bar on every frame (reuse the T-0072 caption helper), per-frame
  `quantize(data, 256, { format: 'rgb565' })` + `applyPalette`, delay 83,
  infinite loop. Toasts: `REC ●` at start, `ENCODING…` when capture ends,
  `POSTCARD SAVED` on download. Re-entrant calls while recording resolve
  the SAME in-flight promise (no concurrent recordings).
- `Shift+P` in the `main.ts` keydown listener (T-0072 left it a no-op);
  menu button `RECORD GIF (3S)` under `SAVE PNG`, same dismiss-then-run
  pattern; `__asciicity.postcard('gif')` now resolves.
- Filename `asciicity-<city>-<yyyymmdd-hhmmss>.gif` (reuse
  `postcardFilename` with an extension argument).
- Pure + unit-tested additions to `tests/postcard.test.ts`: the sampling
  schedule (e.g. `gifSchedule(durationMs = 3000, fps = 12)` → 36 timestamps
  83.33 ms apart), scale rule (1920 → 0.5; 800 → 1), filename with `.gif`.
- e2e additions to `e2e/postcard.spec.ts`:
  1. `__asciicity.postcard('gif')` resolves (allow ≥ 20 s timeout —
     SwiftShader is slow); bytes 0–5 === `GIF89a`; logical-screen width
     (bytes 6–7, little-endian) ≤ 960; size ≤ 15 MB.
  2. `Shift+P` fires a `download` event with suggested filename matching
     `/^asciicity-\w+-\d{8}-\d{6}\.gif$/`.

### Reviewer notes
- PNG path was moved into a private `flushPng()` so `afterRender` can also sample GIF frames; PNG behaviour is unchanged (`toBlob`, caption below the frame, download+toast only when a waiter asked).
- Capture clock starts on the first `afterRender` after `recordGif` (not at the keypress) so 30/144 fps both yield 36 frames over ~3 s of wall-clock video. A stalled loop still emits 36 frames by duplicating the current canvas.
- Encoding is synchronous on the last sampled frame (`ENCODING…` then `quantize`×36); architecture.md says a brief frame-loop stall is acceptable. The `Uint8Array`→`Blob` copy exists only because TS 5.9's `BlobPart` rejects `Uint8Array<ArrayBufferLike>`.
- No e2e for the menu button itself — ticket only required the hook + `Shift+P` download cases. No workerised encoding / MP4 (out of scope).
