## Goal
SF is 14.7 MB and Manhattan will be ~20 MB; today the start overlay sits
blank until everything is built. Show progress: a 20-cell ASCII bar with MB
counts while downloading, then PARSING, then BUILDING · <STEP> while the
world is built, then the usual prompt. Contract: `docs/architecture.md`
§4.18 — read it in full first; it is the spec (surface, strings, phases).

## Context
- NEW `src/ui/loading.ts`: `LoadProgress`, `formatLoading` (pure), and
  `loadCityJson(url, sizeHint, onProgress)` (fetch → `body.getReader()` →
  accumulate `Uint8Array` chunks → `TextDecoder` → `JSON.parse`). `total`
  = `Content-Length` when the response has no `content-encoding` header,
  else `sizeHint`; clamp `received` to `total`. Throw the same errors the
  current fetch path throws (keep the existing failure handling in main.ts).
- `src/data/cities.ts`: add `sizeBytes: number` to `CityInfo` and fill it
  for every entry from `stat` of the committed files (`public/data/city.json`,
  `kyiv.json`, `sf.json` — report the numbers). `tests/cities.test.ts`:
  `'every city sizeBytes matches the committed file within 1 %'`.
- `src/main.ts`: find where the city JSON is fetched today (after the picker
  resolves, ≈ lines 370–400) and route it through `loadCityJson`; drive the
  overlay `<p>` with `formatLoading(city.label, p)` while `phase !==
  'ready'`; insert `await nextFrame()` (a `requestAnimationFrame` promise
  helper) between the major builders so the overlay repaints — set
  `step` to the builder that runs NEXT: TERRAIN, BUILDINGS, ROADS, TREES,
  WATER, BRIDGES, TRAFFIC, SHIPS; expose `window.__asciicity.loading` (live
  object). Keep `__asciicity.ready` semantics: true only after the last
  builder. `?synthetic=1`: no download phase — start at `build`.
  Touch only the load/boot sequence and the API object; no renderer,
  HUD or control changes.
- `tests/loading.test.ts`: `formatLoading` for `download` at 0 %, 41 %
  (`[########............] 41% · 6.0 / 14.7 MB`), 100 %; `parse`;
  `build` with a step; `ready` → `''`; `received > total` clamps;
  `loadCityJson` against a stubbed `fetch` (ReadableStream of 3 chunks, no
  content-encoding, Content-Length set) reports monotonically increasing
  `received` and returns the parsed object; with `content-encoding: gzip`
  it uses `sizeHint` as `total`.
- NEW `e2e/loading.spec.ts` (never edit smoke/sf specs): boot
  `/?city=sf&at=unionsquare`, poll `__asciicity.loading.phase` every 50 ms
  until `ready` (90 s timeout), assert the observed set contains `build`
  and the final phase is `ready`, and that `#overlay p` text contains
  neither `LOADING` nor `BUILDING`.
- `docs/integration.md`: a "Loading indicator" note (phases, `sizeBytes`
  must be updated when a dataset is re-fetched, `__asciicity.loading`).

### Notes for the reviewer

- The overlay `<p>` in `src/style.css` has no `white-space: pre`, so the
  `\n` between `LOADING SAN FRANCISCO` and the bar renders as a single
  space in the browser. The spec (§4.18) pins the return value; the
  visible break is a follow-up (out of scope for T-0085).
- The `window.__asciicity` object is replaced once after all builders
  finish (real `api`); the `loading` reference is shared between the early
  stub and the final `api`, so an e2e that captures `__asciicity.loading`
  keeps seeing the same live object across the swap.
- `main.ts` calls `paintLoading()` when flipping to `ready` (setting the
  `<p>` textContent to `''`) so the e2e's post-`ready` text check never
  races the pre-existing `setOverlay(false, true)` → `CLICK TO ENTER`
  write later in main.
- Reordered scene.add order to match the ticket's step labels (TERRAIN,
  BUILDINGS, ROADS, TREES, WATER, BRIDGES, TRAFFIC, SHIPS). The three.js
  depth buffer sorts opaque draws; no visual difference.
