## Goal

The Sydney Opera House is missing from the shipped dataset: OSM maps it as
a building relation whose outer boundary is **16 separate ways**, and the
converter only emits building relations whose outer members are single
closed ways (T-0110 report: one of 24 skipped relations). Teach the
building path to stitch multi-way outer members into closed rings — the
water/woods paths already do exactly this — then refetch Sydney so the
Opera House (and the other skipped relations) land.

## Context

- T-0110's Worker report (`.tigerteam/board/done/T-0110.md`) documents the
  find: relation 9596872, `building=yes`, name `Sydney Opera House`,
  16 outer ways, skipped.
- `scripts/osm-convert.mjs` already contains ring assembly from unordered,
  possibly-reversed way members for water ("Assemble water rings from OSM
  ways/relation members", ~line 257/312) and woods — reuse that helper for
  the building-relation path rather than writing a second stitcher. Keep
  the existing rules: each assembled outer ring becomes one building; the
  first ring keeps the relation id, later rings get unique ids; tags
  (name, height, colour inputs) come from the relation.
- An open (unstitchable) outer boundary stays skipped and counted — never
  emit a partial ring.
- Refetch: `npm run fetch-data:sydney` (same alias/bbox — nothing else
  changes). Expect small drifts vs T-0110's fetch (live Overpass); that is
  fine. The 12 MB guard still applies.
- `sizeBytes` in `src/data/cities.ts` must be updated to the new
  `index.json` size (registry rule).
- The wave-13a in-place-surgery rule does NOT apply here — this is a
  legitimate full refetch (the building set itself changes).
