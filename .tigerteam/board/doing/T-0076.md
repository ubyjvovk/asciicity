**Exact failure** (rerun: `npm run fetch-data:sf`):

```
fetch: closeCoastline: point (-122.4075586, 37.8080734) is not on the bbox perimeter
```

**Root cause (diagnosed with the real Overpass result, saved at `/tmp/coast.json`).**

The SF bbox captures the peninsular Bay shoreline. The Embarcadero coastline
way (id 43008440) ends and the Marina/Presidio coastline way (id 32648495)
begins at the *identical* node (-122.4075586, 37.8080734) — the Fisherman's
Wharf/Fort Mason bend, an interior point (gap measured: 0.000 m). The
through-coast therefore should be ONE open chain from the bbox south edge to
the bbox west edge, with that node an interior vertex.

`stitchChains` (osm-convert.mjs ~line 443) only ever **appends** a piece to the
*current* chain (`tail == other[0]`), and processes pieces in array order. Here
the Marina piece (which geometrically comes AFTER the Embarcadero piece) is
processed first and absorbs the westward coast, leaving the Embarcadero piece
orphaned with its interior endpoint u. `closeCoastline` then cannot parameterise
 that endpoint on the bbox perimeter and throws.

Rerunnable evidence:

```bash
node /tmp/diag.mjs /tmp/coast.json
# coastline ways: 45, pieces: 46, closed: 5, open: 13
#   open chain 275 pts. start (-122.39172,37.79343) end (-122.40756,37.80807)  <- Embarcadero (orphan)
#   open chain 658 pts. start (-122.40756,37.80807) end (-122.48700,37.78985) <- Marina->GGB->west edge
# closeCoastline threw: closeCoastline: point (-122.4075586, 37.8080734) is not on the bbox perimeter
```

**Recommended fix (backward-compatible; belongs to T-0075/osm-convert.mjs).**
Make `stitchChains` merge-aware: in addition to the current `end→start` append,
also join `other.end→chain.start` (prepend) on coinciding endpoints, and
repeat until no two chains share an endpoint (or run a second pass over the
leftover open chains against the already-built chains before returning). I
prototyped this in `/tmp/diag5.mjs` and, with it, the same real data yields
`closed: 5, open: 3` and `closeCoastline` returns 2 water rings with no crash
instead of throwing — so the current fix is sufficient to unblock SF. It does
not change the existing coastline unit tests (the "single unmatched piece" and
"strait" cases still behave identically).

### PM answer (2026-08-28)

Good diagnosis — confirmed against the source: `stitchChains` only appends
(`tail == o[0]`) and never prepends, so array order decides whether an open
coast survives. **Option B: this ticket's scope is amended** (frontmatter
updated) to include `scripts/osm-convert.mjs` (the `stitchChains` function
ONLY) and `tests/coastline.test.ts` (append cases only). Fix it here, then
carry on with the ticket as written.

Locked design for the fix (this is the contract; data-format.md "Coastline
water" step 3 was amended on main to say the same — do NOT edit
data-format.md and do NOT merge main into your branch, PROTOCOL §6):
- Stitching is independent of array order. On coinciding endpoints (same
  `eps`), a piece may attach AFTER the chain (chain end = piece start) or
  BEFORE it (piece end = chain start). Loop until no unused piece matches
  either end (or the chain closes).
- NEVER reverse a piece: way direction carries the land-left/water-right
  side that the clockwise closure depends on.
- Existing outputs must be byte-identical for every existing fixture
  (the closed-loop, single-piece, strait and island tests stay untouched
  and green). Export signature unchanged.

Tests to append to `tests/coastline.test.ts` (names verbatim):
- `'joins two open pieces sharing an interior node regardless of array order'`
  — pieces `[B, A]` where `A` ends where `B` starts; expect `open` = one
  chain equal to `A.concat(B.slice(1))` and `closed = []`. Run the same
  assertion with `[A, B]` to prove order-independence.
- `'stitches a three-piece open coast given in the order [middle, last, first]'`
