## Goal
Fetch, convert and commit the Central Tokyo tiled dataset — the first
streamed-only city. Data only: no app code. Expect the largest fetch so
far (112 184 building ways counted at boarding).

## Context
- **Read first**: data-format.md "Central Tokyo (`data/tokyo/`, wave 11)"
  — bbox, origin, flags, budget — and "Tiled datasets" above it.
- Command: `node scripts/fetch-osm.mjs --bbox 139.730,35.645,139.820,35.715
  --origin 139.7671,35.6812 --lang en --dem 1 --chunks 3x3 --tiles --out
  public/data/tokyo`. Off-peak Overpass etiquette: if a chunk 429s/504s,
  wait 60 s and retry that chunk (the endpoints fall back automatically);
  if it keeps failing across both endpoints, file `## Questions` rather
  than hammering.
- Origin is Tokyo Station from the PM's notes — VERIFY it against the
  fetched `railway=station` node named Tokyo (or `name:en` `Tokyo`); if
  the node is > 100 m away, use the node's coordinates instead and state
  the correction in your report (spec-vs-data reconciliation is wanted
  here, per AGENTS.md).
- Verify landmark coverage in the OUTPUT (node one-liners over the tiles
  or index): `index.landmarks` contains entries whose names identify
  Tokyo Skytree and Tokyo Tower (report the exact name strings — with
  `--lang en` they should be the `name:en` values), and max building `h`
  is ≈ 634 (Skytree; the clamp is 650).
- Sanity: `index.tiles` has ≈ 40–72 non-empty keys (8×7 km at 1000 m);
  terrain datum should be ≈ 0–10 m ASL (Marunouchi is near sea level);
  water should include the Sumida river and bay fragments (coastline
  closure) — report ring/river counts.
- **Size budget 60 MB** for index + tiles combined. Over budget → STOP and
  file `## Questions` with the actual numbers (do not trim the bbox or
  thin data on your own).
- Committed data is binary-ish: never `cat` it; inspect with `node -e`.
