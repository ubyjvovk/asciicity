## Goal
Fix the argument parser in `scripts/fetch-osm.mjs`: the documented bare
`--tiles` flag is silently mis-parsed (it consumes the NEXT token as its
value), so `--tiles --out public/data/tokyo` wrote a monolithic
`public/data/city.json` to the default path instead of a tiled directory
(found during T-0097 — the run had to be redone with `--tiles 1`).

## Context
- `parseArgs` in `scripts/fetch-osm.mjs` reads only `--key value` pairs.
  `--tiles` is the script's one boolean flag; `--tiles 1` / `--tiles true`
  are explicitly supported today and MUST keep working (the npm
  `fetch-data*` aliases and docs/data-format.md use `--tiles 1`).
- Required behaviour: `--tiles` followed by another `--flag` (or nothing)
  parses as `tiles = true` and does NOT consume the following token.
  Any other unknown `--key` whose next token is also a `--flag` should
  error out loudly (`unknown or valueless flag --<key>`) instead of
  silently mis-pairing — the silent fallthrough to the default `--out` is
  the dangerous part of this bug.
- Extract the parser into an exported pure function if it is not one
  already, so it is unit-testable without network (same pattern as
  `splitBbox`/`dedupeElements` from T-0093).
