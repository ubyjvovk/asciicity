## Goal
San Francisco is next, and its water is `natural=coastline` — ways, not
polygons — which the converter currently ignores entirely: the Bay would
render as flat walkable ground. Implement `docs/data-format.md`
"Coastline water" rules 1–6 exactly (read that section first; it is the
contract, including the clockwise boundary-closure walk, the island rule
and the flattening parity).

## Context
- `scripts/osm-convert.mjs`: existing water assembly is around
  `assembleRings` (~line 200–260) and the water block (~line 714–760);
  ring clipping/cleaning helpers around line 169. New pure, exported
  functions (so tests can hit them directly), e.g.
  `clipPolylineToBbox(points, bbox)`, `stitchChains(pieces)`,
  `closeCoastline(chains, bbox)` → rings — names up to you, but pure and
  documented. Coastline rings are appended to the same `water` array the
  polygon path fills.
- `scripts/fetch-osm.mjs`: add the `way["natural"="coastline"]` clause to
  the Overpass query (same bbox, `out geom` — mirror the existing
  clauses).
- `scripts/dem.mjs`: the flattening step (~line 246–) switches from
  "inside ring i" to the odd-parity rule (data-format.md Terrain step 4 as
  amended). With no nested rings behaviour is identical — add a regression
  test in `tests/dem.test.ts` proving a non-nested two-ring case flattens
  exactly as before, plus the nested island case (inside outer only →
  flattened; inside outer+island → NOT flattened).
- `tests/coastline.test.ts` (new): the four fixtures named at the end of
  the data-format section (single coast / strait / island + parity /
  no-coastline). Use a unit bbox and hand-computed expected rings —
  assert exact vertex sequences (corners included) so orientation bugs
  cannot hide.
- Do NOT refetch or modify any committed dataset (`public/data/*.json`
  untouched); do not touch `src/` — runtime collision intentionally keeps
  "inside any ring = water" (rule 7).
